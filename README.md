## Модуль предобработки

### Назначение

Модуль предобработки решает задачу приведения разнородных учебных материалов к единому структурированному виду, пригодному для автоматической генерации тестов. Он принимает на вход лекции в форматах PDF, DOCX, TXT, MP3 и MP4, извлекает текстовое содержимое (для аудио и видео — с помощью транскрипции речи), выполняет очистку и нормализацию, выделяет математические формулы и блоки программного кода, разбивает материал на смысловые блоки (чанки) и обогащает их метаданными (тема, ключевые слова, статистика). Результат работы модуля — JSON‑файл, который передаётся генератору тестов на основе GigaChat. 

### Архитектура и компоненты

Модуль построен по конвейерному принципу: каждый этап обработки реализован отдельным классом, а центральный компонент `LectureProcessingPipeline` последовательно вызывает их и передаёт промежуточные результаты. 

Основные компоненты и их роли:

- **`LectureProcessingPipeline` (pipeline.py)** – центральный класс, реализующий полный цикл обработки. Хранит настройки (тип разбиения, размеры чанков, путь к модели Vosk) и по шагам вызывает все остальные модули. Наружу отдаёт объект `ProcessingResult`, на основе которого создается финальный JSON-файл.

- **`cli.py`** – интерфейс командной строки. Принимает путь к файлу, тип разбиения, параметры размеров чанков и запускает `LectureProcessingPipeline`. Реализован с помощью `argparse`.

- **`file_loader.py`** – загрузчики файлов. Содержит абстрактный класс `FileLoader` и конкретные реализации для каждого формата:
  - `TxtLoader` – загрузка `.txt` с автоматическим определением кодировки.
  - `PdfLoader` – извлечение текста из `.pdf` через `PyMuPDF`.
  - `DocxLoader` – извлечение текста из `.docx` (включая таблицы).
  - `AudioLoader` – транскрипция `.mp3` с помощью `Vosk` и `ffmpeg`.
  - `VideoLoader` – извлечение аудиодорожки из `.mp4` через `ffmpeg` и последующая транскрипция.
  - `FileLoaderFactory` – автоматически выбирает нужный загрузчик по расширению файла.

- **`text_normalizer.py`** – очистка и нормализация текста: удаление невидимых символов, унификация переносов строк, нормализация пробелов. Может сохранять плейсхолдеры формул, чтобы не повредить их при очистке.

- **`formula_extractor.py`** – обнаружение математических формул. Поддерживает формулы в формате LaTeX (внутристрочные `$...$` и выключные `\[...\]`), а также эвристический поиск plain‑text формул. Найденные формулы заменяются плейсхолдерами, чтобы не мешать разбиению на чанки, а в финальном результате восстанавливаются.

- **`code_extractor.py`** – выделение блоков программного кода. Распознаёт как явные блоки (Markdown‑разметка с тройными кавычками), так и строки с ключевыми словами, операторами и характерными отступами. Код также временно заменяется плейсхолдерами и восстанавливается после разбиения.

- **`text_splitter.py`** – разбиение текста на чанки. Содержит несколько стратегий (`ParagraphSplitter`, `SemanticSplitter`, `FixedSizeSplitter`, `MixedSplitter`), объединенных общим интерфейсом `TextSplitter`. 

- **`text_cleaner.py`** – удаление нерелевантных фрагментов, характерных для устной речи (приветствия, «вопросы есть?», «перейдём к следующей теме» и т.п.). Применяется к результатам транскрипции аудио/видео.

- **`metadata_extractor.py`** – извлечение метаданных из готовых чанков: определение темы (по ключевым словам), сбор статистики (слов, предложений, лексического разнообразия) и выделение ключевых слов. 

- **`data_models.py`** – датаклассы, описывающие структуры данных, которыми обмениваются компоненты: `TextChunk`, `ProcessingResult`, `ProcessingStats`, `Formula`, `BlockType` и другие.

`Pipeline` вызывает компоненты модуля как отдельные шаги, а данные передаются в виде описанных в `data_models.py` объектов.

### Входные и выходные данные

**Вход**
Модуль принимает файлы пяти форматов:
- `.txt` – текстовый докмент;
- `.pdf` – PDF‑документ;
- `.docx` – документ Word;
- `.mp3` – аудиозапись ;
- `.mp4` – видеозапись (будет извлечена звуковая дорожка).

Для аудио и видео текст получается автоматической транскрипцией речи, поэтому на входе не требуется текстовой расшифровки.

**Выход**
Результат – JSON‑файл. В нём есть две основные части:
- общая информация: путь к исходному файлу, время обработки, общее число чанков и формул;
- массив `chunks` – список смысловых блоков, на которые разбит материал. У каждого блока есть обработанный текст, найденные формулы, тип блока (текст/код) и метаданные (тема, ключевые слова, статистика).

Этот JSON напрямую читается генератором тестов. 

### Требования к окружению

1. **Python** версии 3.9 или выше (лучше 3.10–3.12).
2. **ffmpeg** – программа для конвертации аудио/видео. Она должна быть установлена отдельно и доступна в командной строке.  
3. **Модель Vosk** для распознавания русской речи.  
   - Скачайте архив `vosk-model-small-ru-0.22.zip` с [официального сайта](https://alphacephei.com/vosk/models).  
   - Распакуйте в папку `src/models/vosk-model-small-ru-0.22` (можно указать другой путь через параметр `vosk_model_path`).
 |
Все библиотеки кроме `ffmpeg` устанавливаются автоматически из `requirements.txt`.

### Структура выходного JSON

Ниже пример того, что получается на выходе. 

```jsonc
{
  "process_id": "550e8400-e29b-...",   // уникальный id обработки
  "source_file": "lecture.pdf",        // имя исходного файла
  "processed_at": "2025-05-02T10:00:00",
  "statistics": {
    "total_chunks": 12,                // сколько чанков получилось
    "total_formulas": 5,               // сколько формул найдено всего
    "processing_time_seconds": 1.234,
    "input_file_size_bytes": 456789
  },
  "chunks": [
    {
      "id": "chunk_000001_a1b2c3",     // уникальный id блока
      "sequence": 0,                   // номер по порядку, начиная с 0
      "original_text": "Сегодня рассмотрим закон Ома...", // исходный фрагмент
      "processed_text": "Сегодня рассмотрим закон Ома...", // очищенный текст
      "block_type": "text",            // text, code или mixed
      "formulas": [
        {
          "original": "I = U / R",
          "normalized": "I=U/R",
          "type": "plain_text",
          "position": {"start": 120, "end": 129}
        }
      ],
      "metadata": {
        "word_count": 45,
        "main_topic": "физика",
        "key_terms": ["закон Ома", "ток", "сопротивление"],
        "is_short": false,
        "is_long": false,
        // ... дополнительная статистика
      }
    }
    // ...остальные чанки
  ]
}
```


- `original_text` сохраняется для возможности вернуться к исходной формулировке, если это важно.
- `processed_text` – это то, с чем будет работать генератор тестов. Все формулы и код уже восстановлены из плейсхолдеров.
- `block_type` позволяет генератору понять, что перед ним: обычный текст, программный код или смесь.
- Метаданные (`metadata`) не обязательны для генерации, но могут быть полезны для отладки или фильтрации чанков по темам.

### Стратегии чанкинга в пайплайне

После извлечения и очистки текст нужно разбить на смысловые блоки. В модуле это делает компонент `text_splitter`. Доступно четыре стратегии, выбор задаётся ключом `-s` в командной строке.

- **`paragraph`** (по умолчанию)  
  Каждый абзац становится отдельным чанком. Минимальный чанк – один непустой абзац.

- **`semantic`**  
  Стратегия пытается объединить соседние абзацы, если они говорят об одном и том же. Сравнение идёт не по смыслу слов, а по пересечению длинных ключевых слов (эвристика, без нейросетей). 

- **`fixed_size`**  
  Текст нарезается на блоки примерно одинакового размера (в символах). Между блоками можно настроить перекрытие. 

- **`mixed`**  
  Сначала текст разбивается на абзацы (как в `paragraph`), а затем соседние абзацы объединяются по семантическому принципу (как в `semantic`). 

Размер чанков регулируется параметрами `--min-chunk` и `--max-chunk` (в символах). По умолчанию 100 и 2000. Это позволяет избежать слишком мелких или чрезмерно больших кусков.


## Исследование чанкинга

### Введение и постановка задачи

Первоначально в модуле предобработки текст делился на чанки по абзацам. Для обычных текстовых документов этого было достаточно, но при работе с расшифровками аудио или видео абзацы отсутствуют, и такой подход становится бесполезен.

**Цель работы** — подобрать метод автоматической сегментации, который не опирается на абзацы, но при этом делит текст на логически законченные фрагменты. Метод должен работать для русского языка.

**Гипотеза** состоит в том, что использование семантических эмбеддингов предложений вместе с иерархической кластеризацией даст более точные границы, чем классический алгоритм TextTiling или простое пороговое разделение. Дополнительно запланировано сравнение с обученным нейросетевым классификатором.


### Данные и их подготовка

Для экспериментов выбран открытый датасет **RuTextSegNews** (ссылка: https://huggingface.co/datasets/mlenjoyneer/RuTextSegNews). Это коллекция русскоязычных новостных статей с ручной разметкой границ тематических блоков. Разметка представляет собой последовательность меток: `0` — предложение продолжает текущую тему, `1` — начинается новая тема. На основе этих меток построены эталонные чанки (`chunks_gt`).

Подготовка данных выполнялась в несколько шагов. С помощью скрипта `prepare_boundary_data.py` датасет был загружен, и для каждого предложения вычислены эмбеддинги двумя моделями: `paraphrase-multilingual-MiniLM-L12-v2` (в тексте — **MiniLM**), мультиязычной и хорошо подходящей для задач семантического сходства, и `cointegrated/rubert-tiny2` (**rubert‑tiny2**), лёгкой русскоязычной моделью. Полученные эмбеддинги вместе с предложениями и метками сохранены в файл `rutextseg_processed.json`. Для обучения логистической регрессии были сформированы пары соседних предложений: их эмбеддинги конкатенированы, добавлена метка наличия границы между ними. Эти данные сохранены в `boundary_data.npz`. Тестовая выборка, на которой приведены все результаты, содержит примерно 4000 документов длиной от 5 до 50 предложений.

### Сравниваемые методы

В бенчмарк вошли шесть методов. Четыре из них используют предварительно посчитанные эмбеддинги, один является классическим лексическим, и один основан на статистическом обучении.

1. **TextTiling** — классический алгоритм из библиотеки NLTK (`TextTilingTokenizer`). Он разбивает текст, анализируя сходство слов в соседних окнах. В эксперименте использованы параметры `w=15` (псевдопредложений в окне) и `k=5` (число ближайших соседей). Эмбеддинги не применяются.

2. **Greedy (MiniLM)** — простейший эмбеддинговый подход: граница ставится между соседними предложениями, если косинусное сходство их векторов ниже порога 0.5. Этот порог выбран предварительно как дающий разумный баланс между излишней фрагментацией и склеиванием тем. Использованы эмбеддинги MiniLM.

3. **Hierarchical (MiniLM)** — агломеративная иерархическая кластеризация (`AgglomerativeClustering` с метрикой cosine и linkage=average). Наложено ограничение связности: объединять можно только соседние предложения, что превращает кластеризацию в поиск непрерывных сегментов. Число кластеров задано равным истинному количеству чанков в каждом тексте — это оценка максимальных возможностей метода. На практике число кластеров потребуется определять автоматически (например, по «локтю» на дендрограмме), что остаётся задачей для будущего.

4. **Hierarchical (rubert‑tiny2)** — тот же иерархический алгоритм, но на эмбеддингах `cointegrated/rubert-tiny2`. Позволяет оценить влияние выбора модели.

5. **Uniform (k=5)** — равномерное разбиение текста ровно на 5 блоков одинаковой длины. Это наивный бейзлайн, не использующий содержание текста; любой полезный метод должен его превосходить.

6. **Supervised LogReg** — логистическая регрессия, обученная на конкатенации эмбеддингов двух соседних предложений (MiniLM) предсказывать наличие границы. Модель обучается на train‑сплите датасета (80%), предсказания делаются на тестовых документах. Порог вероятности для границы — 0.5. Это попытка напрямую выучить понятие семантического разрыва по парам предложений.

Все методы, кроме Supervised LogReg, не требуют обучающей выборки и работают на одном документе независимо от других.

### Метрики оценки качества

Качество сегментации оценивается четырьмя метриками: три внешние (сравнение с эталоном) и одна внутренняя (оценивает свойства предсказанных сегментов без эталона). Пусть документ состоит из \(n\) предложений, истинные границы закодированы бинарным вектором \(b \in \{0,1\}^{n-1}\) (1 — граница между предложениями \(i\) и \(i+1\)), предсказанный вектор — \(\hat{b}\).

- **Pk (Kappa probability)**. Для окна шириной \(k\) (обычно \(k = \lfloor \text{средняя длина эталонного сегмента} / 2 \rfloor\)) вычисляется доля положений окна, в которых индикатор наличия хотя бы одной истинной границы не совпадает с индикатором для предсказанных границ:
  \[
  Pk = \frac{1}{n-k}\sum_{i=1}^{n-k} \mathbf{1}[B_i \neq \hat{B}_i],\quad B_i = \mathbf{1}\!\left[\sum_{j=i}^{i+k-1} b_j > 0\right],\ \hat{B}_i = \mathbf{1}\!\left[\sum_{j=i}^{i+k-1} \hat{b}_j > 0\right].
  \]
  Чем ниже Pk, тем точнее воспроизведена крупномасштабная структура текста.

- **WindowDiff** заменяет бинарный индикатор на разность количества границ внутри окна:
  \[
  WindowDiff = \frac{1}{n-k}\sum_{i=1}^{n-k} \left| \sum_{j=i}^{i+k-1} b_j - \sum_{j=i}^{i+k-1} \hat{b}_j \right|.
  \]
  Эта метрика штрафует не только за факт ошибки, но и за её величину, и менее чувствительна к вариации длины сегментов.

- **Boundary F1**. Граница считается найденной корректно, если она попадает в окрестность \(\pm 1\) предложения от истинной. Пусть \(T\) — множество позиций истинных границ, \(P\) — предсказанных. Тогда точность и полнота определяются через количество найденных границ, и Boundary F1 вычисляется как их гармоническое среднее. Метрика показывает способность метода не пропускать реальные границы и не создавать ложные, допуская небольшой сдвиг.

- **Intra Similarity** (внутренняя метрика, не требует эталона). Для каждого предсказанного сегмента \(C\) с \(|C| \ge 2\) вычисляется среднее попарное косинусное сходство всех предложений внутри него:
  \[
  \text{sim}(C) = \frac{1}{\binom{|C|}{2}} \sum_{\substack{i,j \in C \\ i < j}} \cos(\mathbf{v}_i, \mathbf{v}_j).
  \]
  Итоговое значение — среднее арифметическое по всем сегментам, содержащим хотя бы два предложения. Высокое значение говорит о тематической однородности блоков, хотя сама по себе эта метрика не гарантирует правильность границ (излишнее дробление может искусственно её завысить).

| Supervised LogReg           | 0.4347 | 0.4538       | 0.2197        | 0.2935             |

Дополнительно вычислены 95% доверительный интервал для Pk у метода Hierarchical (MiniLM): **[0.3195, 0.3303]** — интервал узкий, результат стабилен. Тест Уилкоксона между Hierarchical (MiniLM) и Supervised LogReg дал **p-value ≈ 0.0000**, что подтверждает статистическую значимость различий.

#### Анализ по методам

**Наилучшие внешние метрики** демонстрирует **Hierarchical (MiniLM)**. У него минимальные Pk (0.325) и WindowDiff (0.379), а также максимальный Boundary F1 (0.644) — почти две трети истинных границ обнаруживаются в пределах ±1 предложения. При этом Intra Similarity у него средняя (0.368). Преимущество метода объясняется тем, что он учитывает глобальную структуру документа через кластеризацию, а не принимает решения по каждой паре предложений изолированно.

**Второй по качеству — Hierarchical (rubert‑tiny2)**. У него заметно выше Intra Similarity (0.581) — чанки получаются очень связными, модель хорошо группирует семантически близкие предложения. Однако проигрыш по Pk и Boundary F1 указывает на то, что эта модель иногда объединяет разные темы, которые эксперты разделили. Русскоязычный rubert‑tiny2 тоньше чувствует локальную близость, но может «перетягивать» предложения в соседние темы, смазывая объективные границы.

**Наихудший результат (исключая заведомо слабые бейзлайны) показывает Greedy (MiniLM).** При приемлемом Boundary F1 (0.458) его WindowDiff огромен (1.300) из-за слишком большого числа границ — текст дробится на мелкие куски. Это наглядно демонстрирует, что простое пороговое решение по парам предложений без контекста не работает.

**Supervised LogReg** по Pk и WindowDiff находится на уровне TextTiling, но Boundary F1 очень низок (0.220). Классификатор «размазывает» границы: вероятности часто колеблются около 0.5, не давая чёткого решения. Линейная модель на конкатенированных эмбеддингах двух предложений не способна уловить глобальный контекст документа.

Метод **Uniform (k=5)** ожидаемо слаб, но интересно, что он всё же превосходит TextTiling по Boundary F1 (0.447 против 0.021). TextTiling в данном эксперименте показал крайне низкую точность обнаружения границ, что делает его непригодным для практического использования на новостных текстах.

### Выводы

Для задачи автоматической сегментации текстов (в том числе транскрибированных лекций) наиболее эффективным признан метод иерархической агломеративной кластеризации с эмбеддингами `paraphrase-multilingual-MiniLM-L12-v2`. Он обеспечивает лучший баланс между точностью обнаружения границ и семантической однородностью чанков.

В случаях, где приоритетом является максимальная внутренняя связность блоков (например, для выделения ключевых фрагментов), целесообразно использовать `cointegrated/rubert-tiny2` — он даёт самую высокую Intra Similarity.

Простой supervised‑подход (логистическая регрессия на парах предложений) не способен конкурировать с методами, учитывающими структуру всего документа. Это подтверждает важность глобального контекста для задачи сегментации.
